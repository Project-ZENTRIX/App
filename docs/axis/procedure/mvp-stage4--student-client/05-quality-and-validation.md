# 05 - 验收与风险控制

**文档目的**：定义学生客户端在 stage4 的验证范围、验收标准和主要风险，确保实现时不会把桌面端做散。

---

## 1. 验收范围

stage4 的验收重点不在功能数量，而在学习闭环是否成立。

必须能验证：

- 客户端能作为独立子 app 启动
- 可进入一个已授权课包
- 可完成读内容、改代码、运行、提交、看反馈
- 可在网络波动下继续工作
- 可把进度与提交事件同步回 API

---

## 2. 基础验收项

- 新的 Tauri 子 app 可独立启动
- 主工作台结构稳定
- 课包内容可从 Manifest 正常加载
- 运行和提交状态在当前上下文内可见
- 离线与恢复流程有明确反馈

---

## 3. 风险点

### 3.1 过早扩展成类 IDE

如果一开始就做太多开发者向能力，学习主线会被冲散。

### 3.2 本地状态和权威状态混淆

如果进度、提交、判题没有明确的权威归属，客户端很快会出现状态不一致。

### 3.3 缓存策略不先定

如果不先定义缓存和版本策略，后面补离线会很重。

### 3.4 子 app 边界不清

如果桌面端和 Web 端共享页面层逻辑过多，后续维护成本会很高。

---

## 4. 质量要求

- 重点页面不能因为空数据崩掉。
- 异常状态必须可恢复，不应只给静态报错页。
- 文案要清楚区分“本地保存”和“已同步成功”。
- 布局要能容纳目录、说明、编辑器和输出区同时存在。

---

## 5. 回归策略

建议优先回归以下路径：

1. 启动恢复
2. 课包进入
3. 编辑运行
4. 提交判题
5. 断网恢复
6. 版本更新
7. 授权失效

---

## 6. 最终验收标准

- 学生可以不依赖 Web 完成一节课的主要动作。
- 客户端对离线、同步失败和版本不一致有明确处理。
- 主工作台、缓存和状态边界稳定，后续功能可以在这个基础上扩展。

_本文档收口 stage4 的质量门槛，作为实现前的最后一层约束。_
