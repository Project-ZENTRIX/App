# 05. 切换、验证与回滚方案

## 1. 切换目标

- 让 Supabase 成为新的数据库和认证底座
- 让现有业务在切换期尽量保持可用
- 让任何回退都能回到一个已知可恢复状态

---

## 2. 建议切换顺序

1. 先切基础 schema 和只读内容
2. 再切 auth 与 profile
3. 再切进度、设备、授权和偏好
4. 再切订单、支付和订阅
5. 最后切运行、提交、判题和审计类高频写表

---

## 3. 验证清单

### 3.1 数据层

- 表、外键、唯一约束、索引都已建好
- 数据行数、抽样记录和关键聚合值一致
- 历史软删除和归档字段能正常工作

### 3.2 Auth 层

- 注册、登录、重置密码、OAuth、退出都可用
- profile trigger 能稳定创建业务资料
- session / token 续期行为符合预期

### 3.3 RLS 层

- 未登录用户只能看到公开数据
- 普通用户只能看到自己的数据
- 管理员 / 教师只能看到属于自己 tenant 或角色允许的数据
- service role 只在服务端可用

### 3.4 业务层

- 课程浏览、学习进度、授权、订单、支付回调都能走通
- web 和 api 的返回值与状态标记一致

---

## 4. 风险点

- 主键类型不统一带来的迁移复杂度
- 现有 `user` / `session` / `account` 与 Supabase Auth 的语义冲突
- 业务写路径和 RLS 规则不同步
- 订单、支付、webhook 的幂等性问题
- 一次性改太多表，导致回滚困难

---

## 5. 回滚策略

### 5.1 原则

- 切换前必须保留旧数据库备份和迁移快照
- 每一阶段只切一组可控能力
- 新旧链路不要同时长期并行写同一批敏感表

### 5.2 回滚触发条件

- 登录失败率显著升高
- RLS 导致核心数据读不到
- 支付或授权链路出现不可逆错误
- 数据核对出现明显偏差

### 5.3 回滚动作

1. 停止切入 Supabase 的新写路由
2. 把流量退回旧 Prisma 路径
3. 用备份恢复受影响的表
4. 复盘迁移 SQL 和 RLS policy 后再重试

---

## 6. 完成标准

- Supabase Auth 已替代应用层自实现 auth 主路径
- `supabase/migrations` 已成为数据库变更主来源
- RLS 已覆盖所有暴露表
- 前端和后端都已切换到新的认证与数据访问方式
- Prisma 只剩下临时兼容层，或者已经完全移除
