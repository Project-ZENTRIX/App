# 03 - Web 登录到 Desktop 的验证链路

**文档目的**：定义用户如何先在 Web 完成登录，再通过 Device Flow / Auth Code Flow 把授权带到 Desktop。

**核心要求**：

- 登录动作以 Web 为主入口。
- Desktop 负责接收和落地授权结果。
- 验证必须可撤销、可过期、可追踪。
- Desktop 不应直接承担完整账号体系输入体验。

---

## 1. 设计结论

你希望的验证机制可以概括为：

1. 用户先在 Web 端登录。
2. Web 端生成一次性授权结果或设备绑定过程。
3. Desktop 通过 Device Flow / Auth Code Flow 接收授权。
4. Desktop 将授权换成本地会话和设备态。
5. 后续访问课包、同步、提交都基于该会话。

这个链路比在 Desktop 里重新做一套完整登录表单更稳，也更符合“Web 负责身份，Desktop 负责执行”的分工。

---

## 2. 推荐流程

### 2.1 Web 发起

- 用户在 Web 登录。
- Web 显示“连接 Desktop”的入口。
- Web 端为当前会话创建一次性授权码或设备绑定令牌。
- 该令牌必须有短过期时间和单次使用约束。

### 2.2 Desktop 拉起

- Desktop 显示“正在等待 Web 授权”的页面。
- Desktop 生成本地设备标识和接入上下文。
- Desktop 轮询或等待后端确认授权结果。

### 2.3 授权交换

- 用户在 Web 完成确认后，Desktop 用授权码向 API 交换访问会话。
- API 校验授权码是否匹配用户、设备和有效期。
- 校验成功后，API 返回 Desktop 可用的会话信息和设备绑定信息。

### 2.4 本地落地

- Desktop 保存必要的本地会话引用。
- 桌面端状态切换为“授权有效”。
- 后续操作直接带着该授权访问 API。

---

## 3. 与现有能力的关系

当前仓库里已经存在的能力可以作为这条链路的基础：

- Web 有现成的登录与账户入口。
- API 已有 auth、session、device 和 license 相关能力。
- 设备绑定和授权事件已经有记录路径。

stage5 要做的是把这些能力串成面向 Desktop 的明确流程，而不是让它们散落在不同页面里。

---

## 4. 安全要求

- 授权码必须短时有效。
- 授权码必须单次使用。
- 授权码要绑定设备或会话上下文。
- Desktop 端不得长期保存可直接复用的高权限明文凭据。
- 任何授权失败都要给出明确状态，避免“看起来像登录了，其实没有”的假象。

---

## 5. UI 交互要求

Desktop 的验证页至少应展示：

- 当前是否等待 Web 授权
- 当前设备信息
- 当前授权状态
- 授权成功或失败提示
- 可重试或重新绑定入口

Web 的确认页至少应展示：

- 当前登录账号
- 当前设备名称或识别信息
- 是否确认授予 Desktop 访问权
- 授权剩余时间

---

## 6. 错误与回收

需要明确处理这些情况：

- 用户在 Web 端取消授权
- 授权码过期
- 授权码已被使用
- Desktop 与 Web 会话不一致
- 设备数量超限
- 绑定关系被管理员或用户主动撤销

任何一种失败都应让 Desktop 退回到可重新发起流程的状态。

---

## 7. 目标结果

完成后，Desktop 的登录不再是独立孤岛，而是通过 Web 的身份确认和 API 的授权校验获得可信会话。
