# 01 - 客户端组装计划

**文档目的**：定义当前 `apps/desktop` 如何和 Web、API、课包内容与本地存储组装成完整的学习执行端。

**设计边界**：

- 这里讨论的是 Desktop 客户端的接入顺序和模块边界，不重新设计整套产品。
- Web 端继续承担账户、购买、设备管理与授权入口。
- API 端继续承担认证、设备、内容与进度的权威逻辑。
- Desktop 端只负责学习执行、本地可用性和体验整合。

---

## 1. 现状判断

当前 `apps/desktop` 已经有基础壳层：

- React 前端入口已经存在。
- Tauri Rust 入口已经存在。
- 目前桌面端更像一个静态工作台原型，而不是连接了真实身份、课包和同步能力的客户端。

这意味着 stage5 的目标不是重做界面，而是把已有壳层接上真实系统。

---

## 2. 组装目标

### 2.1 入口层

- Desktop 启动后先检查本地会话、设备授权状态和课包缓存状态。
- 如果未登录或授权失效，跳转到登录 / 授权接力页。
- 如果已登录但课包未缓存，先拉取课包索引和本地可用状态。
- 如果授权有效且课包已准备好，直接进入学习工作台。

### 2.2 业务层

- 学习工作台要同时承载目录、编辑、运行、日志、提交和反馈。
- 课包内容加载和课程状态展示必须与本地缓存一致。
- 同步逻辑要能处理离线编辑、重新联机和冲突提示。

### 2.3 系统层

- Web 用于产生登录态、授权码、设备绑定入口和用户可见的账户信息。
- API 用于验证 token、发放设备授权、提供课包元数据和提交结果。
- Rust 层用于文件系统、持久化、系统调用和 Tauri 命令编排。

---

## 3. 推荐组装顺序

### 3.1 第一步：统一身份前置条件

先把 Desktop 识别用户身份所需的数据结构固定下来：

- 当前用户
- 当前设备
- 当前授权
- 当前课包版本
- 本地缓存版本

没有这些状态，后面的学习工作台只能做假数据。

### 3.2 第二步：接入 Web 授权入口

在 Desktop 内提供明确的授权接入页，用户可以：

- 在 Web 完成登录
- 在 Web 端确认设备授权
- 把授权状态带回 Desktop

### 3.3 第三步：接入课包壳层

Desktop 应先支持：

- 课包列表
- 课包详情
- 章节与课时树
- 本地缓存可用标识

之后再接编辑器和运行器。

### 3.4 第四步：接入执行能力

在 UI 稳定后，再接：

- 编辑器
- 本地运行命令
- 提交命令
- 日志与错误输出
- 同步与恢复

---

## 4. 组件边界

### 4.1 Web

- 登录、注册、密码找回
- 设备绑定 / 解绑
- 课包购买和查看
- 账户与授权管理

### 4.2 Desktop

- 学习工作台
- 课包本地查看和学习
- 运行、提交、反馈
- 本地缓存和离线处理

### 4.3 API

- session / auth
- device / license
- content pack / progress / submission
- 授权校验和回收

### 4.4 Rust Backend

- Tauri 命令
- 系统文件访问
- 本地配置与缓存
- 进程控制与平台调用

---

## 5. 结构性约束

- Desktop 不直接成为内容作者工具，除非后续另立编辑模式。
- Web 不承担课包内代码编辑与运行。
- API 不渲染 UI，不持有桌面交互状态。
- 所有端共享的状态语义必须一致，尤其是授权、缓存、同步和提交结果。

---

## 6. 目标结果

完成后，`apps/desktop` 不再只是一个空壳，而是能够稳定进入学习执行流程，并和 Web、API、Rust 后端形成明确分工。
