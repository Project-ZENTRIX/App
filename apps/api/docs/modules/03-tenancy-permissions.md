# 多租户与权限

这份文档是 API 层最关键的一份之一。它决定谁能看什么、改什么、属于哪个工作区。

---

## 1. 多租户模型

用户已经明确选择了多租户，所以 API 不能按单工作区假设来写。

### 1.1 租户边界

每个需要共享数据的业务对象都应该能归属到一个租户，例如：

- 内容包
- 课程
- 发布任务
- 订单可见范围
- 管理操作范围
- 授权和设备

### 1.2 租户成员

建议有一张 `tenant_memberships` 作为权限核心。

它至少要表达：

- 谁属于哪个租户
- 这个人在租户里的角色是什么
- 成员状态是否有效
- 成员何时加入

---

## 2. 角色模型

当前 Web 侧已经在用 `student / teacher / admin` 的角色语义，所以 API 规划要和这套语义对齐，而不是另起一套完全不同的名字。

建议做法是：

- 保留产品角色：`student`、`teacher`、`admin`
- 如果后续需要平台级操作，再单独引入 `platform_admin` 或等价概念

这样 UI 的角色切换和 API 的权限判断能一致起来。

---

## 3. RLS 和 API 的分工

### 3.1 RLS 做什么

- 兜底租户隔离
- 兜底用户所有权
- 兜底公开只读状态

### 3.2 API 做什么

- 解释业务规则
- 判断当前动作是否允许
- 选择读写路径
- 记录审计
- 组织跨表事务

不要把“是否允许”的判断完全交给前端，也不要把复杂规则塞进单条 RLS policy 里。

---

## 4. 典型权限对象

规划时要明确这些对象的权限：

- 课程可见性
- 内容包可编辑性
- 订单可见性
- 设备绑定权限
- 授权续期权限
- 系统设置权限
- 管理后台权限

不同对象可能有不同的角色要求，所以权限不要只写成一个通用布尔值。

---

## 5. 建议的数据结构

多租户层建议至少有：

- `tenants`
- `tenant_memberships`
- `tenant_invites`，如后续要邀请制
- `tenant_roles` 或等价角色定义

如果后面需要更细权限，可以在租户角色之外再加资源级权限表，但 MVP 先不要过度设计。

---

## 6. 工作区切换

前端现在已有团队和角色切换样板，所以 API 规划里应明确：

- 当前 active tenant 是哪个
- 当前 active role 是哪个
- 切换后应返回哪些可见范围

也就是说，API 不只做静态鉴权，还要能返回“当前上下文下用户能看到什么”。

---

## 7. 权限判断的输出

建议在关键接口返回里附带：

- `permissions`
- `role`
- `tenantId`
- `membershipStatus`
- `isAdmin`
- `isTeacher`

前端可以直接据此控制导航、按钮和空状态。
