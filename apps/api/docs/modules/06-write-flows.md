# 写入流程与事务边界

这份文档只讲写操作怎么落地。API 作为权威层，真正需要谨慎的就是写入顺序、幂等和状态流转。

---

## 1. 总原则

写操作不要直接暴露给前端数据库层，而应经过 API 服务编排。

每次写入都要想清楚：

- 谁可以写
- 写到哪张表
- 是否需要事务
- 是否需要幂等键
- 写完要不要发事件
- 失败后怎么回滚

---

## 2. 注册和初始化

注册完成后，建议做这些初始化：

- 创建 profile
- 创建默认偏好
- 创建默认通知设置
- 建立初始租户成员关系，若产品需要默认工作区

这类初始化最好放到单独的服务方法里，避免散落在控制器里。

---

## 3. 购买和订阅

订单和订阅是最需要事务边界的部分。

### 3.1 创建订单

流程建议是：

1. 读商品信息
2. 校验价格和可购买状态
3. 创建订单和订单项
4. 返回支付所需信息

### 3.2 支付回调

支付回调到来后：

1. 验证签名
2. 检查事件是否重复
3. 更新支付记录
4. 推动订单状态
5. 生成订阅或权益变更
6. 记录审计

### 3.3 幂等性

支付相关写入必须支持幂等，不能因重复 webhook 把状态写坏。

---

## 4. 授权和设备

设备绑定和授权通常要同时更新多个对象：

- 设备
- 绑定关系
- 授权状态
- 事件历史

建议把“绑定成功”视作一个完整事务，避免设备表和授权表状态不一致。

解绑同理，要同时处理状态回收和历史留痕。

---

## 5. 学习进度

学习进度适合事件驱动，而不是每次都直接改最终聚合值。

建议流程：

1. 写入进度事件
2. 异步或同步聚合当前状态
3. 更新可查询进度视图
4. 保留事件历史

这样后续出问题时可以回放。

---

## 6. 运行与提交

运行和提交也应该分成：

- 创建请求
- 处理结果
- 保存日志
- 更新状态

不要把一次运行的所有动作都塞在一个同步 HTTP 请求里。

---

## 7. 内容发布

内容发布建议按草稿、审核、发布、回滚几个状态推进。

最少要有：

- 草稿保存
- 提交审核
- 审核通过
- 发布生效
- 版本回滚

每一步都应该带上操作者、时间和原因。

---

## 8. 事务和事件的分界

需要事务的：

- 创建订单
- 支付确认
- 设备绑定
- 设备解绑
- 资料修改
- 权限变更

适合事件驱动的：

- 进度上报
- 支付通知
- 运行完成
- 邮件通知
- 审计记录扩散

---

## 9. 错误处理

写入失败时，API 要明确返回：

- 是校验失败
- 是权限失败
- 是重复提交
- 是第三方回调失败
- 还是系统异常

不要把所有失败都糊成一个 500。
