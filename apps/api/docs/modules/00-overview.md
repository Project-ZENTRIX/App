# 总体说明

这份文档描述 `apps/api` 的整体边界和规划原则。这里把 API 视作 ZENTRIX 的权威数据操作层，而不是一层简单的请求转发。

---

## 1. 目标定位

API 层的职责不是渲染页面，而是统一处理：

- 身份验证
- 权限判断
- 业务规则
- 数据读写
- 状态流转
- 审计记录
- 异步回调

前端的所有关键数据都应经过这层，不直接把业务规则散落在 Web 或 Desktop 端。

---

## 2. 当前技术前提

规划时默认这些前提成立：

- 后端实现继续使用 NestJS
- Supabase 是 BaaS
- Supabase 负责 Auth、数据库和 Storage
- API 层是业务编排和权威写入入口
- 业务数据通过 RLS 做防线，但最终逻辑仍由 API 控制

这意味着：

- 浏览器和桌面端不拿 service role key
- 普通请求尽量按用户身份通行
- 高权限写入只在服务端发生

---

## 3. MVP 范围

这次规划按 MVP 来看，不把所有远期能力一次性塞满。

MVP 应该先覆盖：

- Supabase Auth 接入
- 当前用户和资料
- 多租户与角色
- 课程与内容查询
- 学习进度
- 订单、订阅和支付回调
- 设备和授权
- 运行与提交
- 管理后台基础面
- Webhook 和异步任务入口

成就、等级、第三方内容入驻、更复杂的运营后台可以保留接口位，但不要求在第一轮完全做满。

---

## 4. 设计原则

### 4.1 权威优先

所有关键状态以 API 和数据库为准，前端只显示和触发动作。

### 4.2 领域分层

先按业务域拆，再在域内拆读写。

### 4.3 RLS 防线

RLS 不是主逻辑，但必须从第一天就开着。它是后端和数据库之间的最后一层边界。

### 4.4 写入可追踪

订单、授权、进度、提交、管理操作都必须能回放、能审计、能定位来源。

### 4.5 异步与同步分离

像支付、判题、文件处理、汇总类任务不要和用户请求绑死在一条同步链路里。

---

## 5. 规划输出

后续 API 实现应落在这些模块里：

- 认证与会话
- 用户和资料
- 多租户与权限
- 内容和学习
- 商业化和授权
- 运行和提交
- 管理和运维
- Webhook 和后台任务

这份规划只定义边界和处理方式，不强行把代码目录写死，但模块名应尽量与业务域一致。
