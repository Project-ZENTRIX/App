# Supabase 基础层

这份文档只讲 Supabase 在 API 层里的用法，不讲具体业务实体。

---

## 1. Supabase 的角色

Supabase 在这里承担三件事：

- Auth
- PostgreSQL 数据存储
- Storage

API 层负责把这些能力组织成可控的业务操作，不让前端直接碰权威写入面。

---

## 2. 客户端分层

建议至少分三种访问方式：

### 2.1 管理客户端

用于：

- 后台任务
- Webhook 处理
- 迁移或修复脚本
- 高权限管理操作

特征：

- 只在服务端存在
- 使用 service role
- 不受普通用户 RLS 限制

### 2.2 用户上下文客户端

用于：

- 普通请求的读写
- 需要按用户身份走 RLS 的场景

特征：

- 带入当前用户 JWT
- 让数据库层按 user context 继续做约束
- 适合资料、进度、已购资产、个人设置这类数据

### 2.3 公共只读客户端

用于：

- 公开内容
- 公开商品
- 营销页所需数据

特征：

- 只做只读查询
- 读权限由 RLS 或公开 view 控制

---

## 3. 环境变量

API 层至少要规划这些环境变量：

- `SUPABASE_URL`
- `SUPABASE_ANON_KEY`
- `SUPABASE_SERVICE_ROLE_KEY`
- `SUPABASE_JWT_SECRET` 或等价验签材料
- `SUPABASE_STORAGE_BUCKET_*` 的分桶配置

如果后面有环境隔离，还应按 dev / staging / prod 分开管理。

---

## 4. RLS 策略

RLS 的基本思路是：

- 所有租户表都带 `tenant_id`
- 所有用户自有表都带 `user_id`
- 公开数据只允许公开状态查询
- 写入尽量只允许服务端或明确授权角色

RLS 负责兜底，不负责承载复杂业务判断。

---

## 5. Storage 规划

如果文件和附件走 Supabase Storage，建议一开始就按用途分 bucket，而不是塞在一个桶里。

可先规划这些类型：

- 头像
- 课件和封面
- 内容包附件
- 提交产物
- 运行日志或导出文件
- 临时上传文件

每类 bucket 的访问策略应该不同：

- 公开资源可读
- 私有资源按租户或用户控制
- 临时文件应自动过期或可回收

---

## 6. 数据访问方式

### 6.1 读请求

优先读视图或聚合结果，减少控制器自己拼接太多关联数据。

### 6.2 写请求

写入必须经过 API 层业务逻辑，再落 Supabase。

### 6.3 事务边界

跨表写入尽量放在单个服务方法里处理，必要时通过数据库函数或事务封装保证一致性。

---

## 7. 与前端的边界

前端不应该：

- 直接拿 service role key
- 直接承担权威写逻辑
- 绕过 API 自己改主表

前端可以做的只有：

- 带用户 token 调用 API
- 上传文件到受控 Storage 流程
- 展示 API 返回的结果
