# 身份与认证

这份文档只讲身份、会话、用户资料和认证流程。Supabase Auth 是唯一的登录身份来源。

---

## 1. 核心判断

### 1.1 认证真相

`auth.users` 是认证真相。

API 不应自己再造一套独立的密码和会话系统，而是围绕 Supabase Auth 做业务封装。

### 1.2 业务身份

业务里真正需要长期维护的，是这些内容：

- 昵称
- 头像
- 简介
- 偏好
- 通知设置
- 会话列表
- 外部账号绑定状态

这些内容应落在业务表里，而不是只放在 auth metadata 里。

---

## 2. 登录流程

建议把登录视为两步：

1. Supabase 完成认证
2. API 根据登录用户补齐业务侧信息

API 层要做的事情包括：

- 校验用户身份
- 初始化 profile 或缺失字段
- 读取当前租户和角色
- 返回前端需要的会话信息

---

## 3. 建议的数据表

MVP 至少规划这些身份相关表：

- `profiles`
- `user_preferences`
- `notification_preferences`
- `user_sessions_snapshot`
- `user_audit_logs`
- `user_identity_links` 或等价的绑定表

这些表不一定都由 API 直接写，但 API 应该把它们视作自己的业务边界。

---

## 4. 典型接口面

这一模块通常会提供：

- 登录态验证
- 当前用户信息读取
- 个人资料修改
- 密码修改
- 邮箱验证状态查询
- 会话列表查询
- 单会话注销
- 第三方账号绑定与解绑

---

## 5. 注册和初始化

注册后，API 需要补齐的通常有：

- `profiles` 初始记录
- 默认偏好
- 默认通知配置
- 默认租户成员关系，若这是产品启动时的设计要求

这些初始化动作最好是可重复执行的，不要依赖一次性的手工脚本。

---

## 6. 会话处理

建议把会话当作可查询、可失效、可审计的对象。

API 要能回答这几个问题：

- 这个人现在有没有登录
- 这次登录来自哪里
- 最近一次活跃是什么时候
- 哪些会话可以注销

前端页面中的“会话管理”应该直接消费这类能力。

---

## 7. 返回规范

身份类接口建议稳定返回这些字段：

- `user`
- `profile`
- `session`
- `identityProviders`
- `emailVerified`
- `mfaEnabled` 或预留字段
- `activeTenant`
- `activeRole`

这样 Web 和 Desktop 端拿到的数据结构会更统一。
