# Webhooks、异步任务与 Storage

这份文档讲那些不适合直接塞进同步接口里的东西：外部回调、长任务和文件处理。

---

## 1. Webhook 入口

MVP 阶段最重要的 webhook 是支付回调。

它的基本要求是：

- 验签
- 幂等
- 能重放
- 能审计
- 失败有明确记录

如果后面还有其他外部系统，再按同样规则加入口，不要把 webhook 写成一个巨大的通用接收器。

---

## 2. 异步任务

适合异步化的任务包括：

- 运行结果聚合
- 进度汇总
- 通知发送
- 文件处理
- 目录或索引重建
- 订阅状态补偿

MVP 阶段不用一开始就上复杂队列，但 API 规划里要先预留“任务表 / 事件表 / 重试机制”这种抽象。

---

## 3. 事件记录

无论以后用什么队列，最好都保留一条事件/任务记录链路，至少包括：

- 类型
- 来源
- 关联对象
- 当前状态
- 重试次数
- 最近错误
- 创建时间
- 完成时间

这样后续追问题不会只剩日志。

---

## 4. Storage 策略

Supabase Storage 适合放这些东西：

- 头像
- 封面图
- 课件附件
- 提交产物
- 临时导出文件

建议按用途分桶，不要把所有文件堆到一个 bucket 里。

---

## 5. 上传方式

推荐思路是：

1. API 校验上传权限
2. API 生成受控上传方式或写入意图
3. 客户端上传到 Storage
4. API 再回写文件元数据

这样可以保住权限和元数据一致性。

---

## 6. 文件元数据

文件本身在 Storage，业务信息应在数据库里有对应记录，例如：

- 文件名
- MIME 类型
- 所属租户
- 所属内容包
- 所属用户
- 尺寸
- 存储路径
- 可见性

不要只靠路径字符串猜这个文件是什么。

---

## 7. 失败补偿

异步任务和 webhook 都要能补偿：

- 重试
- 幂等跳过
- 手工重放
- 管理员修复

这是权威层必须有的韧性。
