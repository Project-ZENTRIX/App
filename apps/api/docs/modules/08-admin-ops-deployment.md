# 管理、运维与发布

这份文档讲 API 层如何被管理、如何被观察，以及怎么发布和验证。

---

## 1. 管理接口

管理面主要服务内部角色，不应该和普通用户接口混在一起。

建议覆盖：

- 用户管理
- 内容管理
- 授权管理
- 系统状态
- 审计日志
- 功能开关

管理接口应要求更高权限，并且所有写操作都要留审计。

---

## 2. 审计

API 层里的高风险动作都应记录审计，尤其是：

- 权限变化
- 订单修正
- 授权修改
- 设备解绑
- 内容发布
- 功能开关调整

审计记录至少要能回答：

- 谁做的
- 对什么对象做的
- 什么时候做的
- 改了什么
- 结果如何

---

## 3. 日志和追踪

规划时建议把这些都做进统一请求上下文：

- request id
- 当前用户 id
- 当前租户 id
- 角色
- 接口名
- 失败原因

这样后面查问题会省很多时间。

---

## 4. 错误策略

API 的错误输出应该区分：

- 校验错误
- 权限错误
- 不存在
- 冲突
- 重复提交
- 第三方失败
- 系统异常

前端只要知道自己该怎么处理，不需要猜错误来自哪里。

---

## 5. 部署和迁移

MVP 阶段的发布顺序建议是：

1. 先定 Supabase schema 和 RLS
2. 再定 API 模块和接口面
3. 再跑迁移和种子
4. 最后做 Web 联调

如果需要回滚，优先保证数据库迁移和接口兼容，不要只回滚应用代码。

---

## 6. 测试策略

至少要覆盖这些层面：

- 身份验证
- 租户隔离
- 权限判断
- 订单和支付幂等
- 设备绑定和解绑
- 进度写入
- webhook 重放
- 管理接口审计

MVP 阶段的测试重点不是追求覆盖率数字，而是把高风险路径压住。

---

## 7. 发布节奏

建议把 API 发布拆成三类节奏：

- 基础能力先发
- 业务域分批发
- webhook 和异步能力最后收口

这样可以让 Web 和 Desktop 逐步接入，而不是等整套接口全完才开始联调。
